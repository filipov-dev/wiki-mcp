# Справочник CLI

```text
wiki-mcp <команда> [флаги]
```

| Команда | Назначение |
| --- | --- |
| [`connect`](#connect) | Подключить сервер к Claude Code или Codex одной командой. |
| [`serve`](#serve) | Запустить MCP-сервер через stdio или по HTTP ([`--http`](#serve---http)). |
| [`auth`](#auth) | Управлять токенами и организациями профилей: `login`, `status`, `logout`. |
| [`call`](#call) | Вызвать инструмент сервера из консоли с правами профиля. |
| [`ui`](#ui) | Интерактивный просмотр профилей, их прав, регистраций в клиентах и токена. |
| [`tools`](#tools) | Показать и проверить пользовательские инструменты из `tools.toml`: `list`, `check`. |

`wiki-mcp --version` печатает версию, `wiki-mcp <команда> --help` — справку по команде.

## Профили

Профиль — имя, под которым хранятся токен и настройки одного клиента. Профиль по умолчанию для `serve`, `call` и `auth` — `default`, другой выбирается флагом `--profile`; `connect` по умолчанию называет профиль по имени клиента.

- **Токен** — только в системном хранилище: macOS Keychain, Secret Service в Linux, Credential Manager в Windows. Сервис `dev.filipov.wiki-mcp`, учётная запись — имя профиля. Из переменных окружения и `.env` токен не читается, в `profiles.toml` не пишется и не печатается ни одной командой.
- **IAM-токены из источника** — профиль федеративного или сервисного аккаунта Yandex Cloud может не хранить токен, а получать его сам: через `yc iam create-token` или по ключу сервисного аккаунта. Ключ хранится в том же системном хранилище, учётная запись `<профиль>:service-account-key`; токены — только в памяти процесса. Подробности — в [IAM-токенах](iam.md).
- **Настройки** (без токена) — в `~/.config/wiki-mcp/profiles.toml`; в Linux учитывается `XDG_CONFIG_HOME`, в Windows файл лежит в `%APPDATA%\wiki-mcp\profiles.toml`. Файл создают `connect` и `auth login`:

  ```toml
  [profiles.default]
  client = "codex"           # клиент, в котором профиль зарегистрирован через connect
  client_id = "<ClientID>"   # OAuth-приложение пользователя, необязательно
  token_type = "oauth"       # или "iam"
  # iam_source = "yc"        # только для IAM: "yc" или "service-account-key", см. iam.md
  allow_write = false
  allow_destructive = false
  # allow_path = ["/path/to/dir"]   # дополнительные каталоги для локальных файлов
  toolsets = []

  [profiles.default.org]
  type = "yandex360"         # или "cloud"
  id = "<ID организации>"
  ```

Организация обязательна: Wiki принимает запросы только с её ID. Тип определяет заголовок:

| `type` | Организация | Заголовок |
| --- | --- | --- |
| `yandex360` | Yandex 360 для бизнеса | `X-Org-Id` |
| `cloud` | Yandex Cloud Organization | `X-Cloud-Org-Id` |

ID организации показан в панели администратора Yandex 360 (для Yandex 360) или в консоли Yandex Cloud Organization (для Yandex Cloud). ID — 1–64 символа из `A-Z`, `a-z`, `0-9`, `-`, `_`.

Тип токена (`token_type`) определяет схему заголовка `Authorization`:

| `token_type` | Токен | Заголовок |
| --- | --- | --- |
| `oauth` (по умолчанию) | OAuth-токен Яндекса | `Authorization: OAuth <токен>` |
| `iam` | IAM-токен Yandex Cloud, живёт не больше 12 часов | `Authorization: Bearer <токен>` |

С `token_type = "iam"` поле `iam_source` говорит, откуда брать токен: `token` (по умолчанию, в файл не пишется) — сохранённый токен; `yc` — `yc iam create-token` (с `yc_path` и `yc_profile`); `service-account-key` — ключ сервисного аккаунта из системного хранилища. С `yc` и ключом сервер сам обновляет токен до истечения срока, см. [IAM-токены](iam.md).

`allow_destructive = true` подразумевает запись: при сохранении профиля `allow_write` выставляется тоже. Пустой `toolsets` — наборы по умолчанию.

### Права профиля

Уровень доступа (`allow_write`, `allow_destructive`) и дополнительные каталоги для локальных файлов (`allow_path`) — граница доступа сервера: `serve`, `call` и `ui` не дают больше. Без них — только чтение. Меняет права [`wiki-mcp ui`](#ui) (вкладка Access), [`connect`](#connect) с `--allow-write` или `--allow-destructive` или правка файла.

- На macOS права сверх чтения действуют только после одобрения владельцем: одобренная копия прав хранится в Keychain (сервис `wiki-mcp.access`, учётная запись — имя профиля), а `ui` и `connect` при повышении прав спрашивают Touch ID или пароль пользователя macOS. Понижение прав одобрения не требует. Если права в профиле шире одобренных, действует пересечение; если одобрения нет или Keychain недоступен — только чтение, сервер предупреждает в stderr.
- В Linux и Windows одобрения нет: права профиля действуют как записаны, а границу задают права токена в Wiki ([Безопасность](security.md#уровни-доступа)).
- Флаги `--allow-write`, `--allow-destructive` и `--allow-path` у `serve` и `call` права только сужают: флаг, который просит больше профиля, — ошибка запуска с подсказкой.

Имя профиля: 1–64 символа из `A-Z`, `a-z`, `0-9`, `.`, `_`, `-`, не начинается с `-`.

### Linux без Secret Service

Запасного файлового хранилища нет. Если в сессии нет демона Secret Service (`org.freedesktop.secrets` на сессионной шине D-Bus), команды `auth` завершаются ошибкой с подсказкой. Запустите демон хранилища: GNOME Keyring, KDE Wallet или KeePassXC с интеграцией Secret Service. На машине без графической сессии можно поднять шину и разблокированное хранилище вручную:

```bash
dbus-run-session -- sh
# внутри новой оболочки; пароль хранилища читается из stdin
gnome-keyring-daemon --unlock --components=secrets
```

Или используйте [HTTP-режим](http.md): там хранилище не нужно.

## connect

```text
wiki-mcp connect <claude-code|codex> [флаги]
```

Подключает сервер к MCP-клиенту: создаёт или обновляет профиль, получает и сохраняет токен и после подтверждения добавляет сервер в конфигурацию клиента. Токен не проходит через агента и не попадает в конфигурацию клиента: туда записывается только команда без флагов доступа

```text
<путь к wiki-mcp> serve --profile <профиль> [--toolsets <a,b>|all]
```

Права — настройка профиля ([права профиля](#права-профиля)). `--allow-write` и `--allow-destructive` меняют их; без этих флагов профиль сохраняет свои права (новый профиль — только чтение). На macOS повышение прав спрашивает Touch ID или пароль пользователя macOS; если подтверждение не получено, права профиля не меняются, а `connect` продолжает подключение с прежними правами. Повторный `connect` перерегистрирует запись старой версии с флагами доступа без них.

| Флаг | По умолчанию | Назначение |
| --- | --- | --- |
| `--profile <имя>` | имя клиента (`claude-code`, `codex`) | Профиль. |
| `--name <имя>` | `wiki` | Имя сервера в конфигурации клиента. |
| `--scope <user\|project>` | `user` | `user` — для всех проектов пользователя; `project` — в `.mcp.json` текущего каталога (только Claude Code). |
| `--allow-write` | права профиля | Задать профилю уровень записи. |
| `--allow-destructive` | права профиля | Задать профилю уровень удаления и изменения прав доступа; включает запись (в профиль сохраняются оба флага). |
| `--toolsets <a,b,…>` | набор `serve` по умолчанию | Наборы инструментов через запятую или `all` — все наборы, включая те, что появятся в новых версиях; неизвестный набор — ошибка. |
| `--client-id <ID>` | из профиля | `ClientID` вашего OAuth-приложения (32 шестнадцатеричных символа). |
| `--org-id <ID>` | из профиля | ID организации Yandex 360 для бизнеса (`X-Org-Id`). |
| `--cloud-org-id <ID>` | из профиля | ID организации Yandex Cloud (`X-Cloud-Org-Id`). |
| `-y`, `--yes` | выкл. | Не задавать вопросов «да/нет»: оставить рабочий сохранённый токен и записать конфигурацию клиента. |
| `--skip-check` | выкл. | Сохранить токен без проверки запросом к API. |
| `--no-browser` | выкл. | Не открывать ссылки в браузере, только напечатать их. |
| `--iam-source <yc\|service-account-key>` | источник профиля | Вместо OAuth-токена получать IAM-токены Yandex Cloud: из `yc iam create-token` или по ключу сервисного аккаунта. Нужна организация Yandex Cloud. |
| `--service-account-key <файл>` | — | Авторизованный ключ сервисного аккаунта (`yc iam key create --output key.json`): содержимое — в системное хранилище, путь не сохраняется. Подразумевает `--iam-source service-account-key`. |
| `--yc-path <путь>` | `yc` из `PATH` | Абсолютный путь к `yc`. Подразумевает `--iam-source yc`. |
| `--yc-profile <имя>` | активный профиль `yc` | Профиль `yc` (`yc --profile`). Подразумевает `--iam-source yc`. |

С флагами IAM (или для профиля, который уже получает IAM-токены сам) шаги 1 и 3 заменяются проверкой источника: OAuth-приложения и токена в хранилище нет, организация — только Yandex Cloud, `connect` проверяет, что источник выдаёт токен, который принимает Wiki. Подробности — в [IAM-токенах](iam.md#подключение).

Шаги:

1. **OAuth-приложение.** Своего приложения в `wiki-mcp` нет: токен выдаёт ваше собственное приложение Яндекс OAuth. Если в профиле ещё нет `client_id` (и не передан `--client-id`), `connect` предлагает взять приложение, уже сохранённое в другом профиле, или открывает страницу создания приложения <https://oauth.yandex.ru/client/new/> и подсказывает настройки:
   - тип — «Для доступа к API или отладки»;
   - название — любое, например `wiki-mcp-<профиль>`, и контактная почта;
   - права — чтение Yandex Wiki (`wiki:read`), а если профилю нужны запись или удаление, также запись (`wiki:write`);
   - Redirect URI, если форма его спрашивает (платформа «Веб-сервисы»), — `https://oauth.yandex.ru/verification_code`.

   Затем спрашивает `ClientID` со страницы приложения, проверяет формат и сразу сохраняет его в профиль: повторный `connect` его больше не спрашивает. `ClientID` не секретный; Client secret не нужен. Если запись включается для профиля, приложение которого создано только с `wiki:read`, добавьте приложению право `wiki:write` и получите новый токен. Почему права лучше давать минимальные и по приложению на агента — в [OAuth-приложении и токене](oauth.md).
2. **Организация** — как в [`auth login`](#auth-login): флаг, профиль или вопрос о типе и ID.
3. **Токен.** Если в хранилище уже есть токен профиля и он проходит проверку, `connect` предлагает его оставить (с `--yes` — оставляет). Иначе открывает ссылку авторизации приложения `https://oauth.yandex.ru/authorize?response_type=token&client_id=<ClientID>`: войдите в аккаунт, от имени которого будет работать агент, разрешите доступ и вставьте показанный токен в скрытый ввод. Токен проверяется запросом `GET /v1/users/me` и сохраняется в системное хранилище; если проверка не прошла, ничего не сохраняется. Без флагов IAM `connect` работает с OAuth-токеном: тип токена профиля становится `oauth`, сохранённый вручную IAM-токен не оставляется.
4. **Профиль.** В `profiles.toml` записываются клиент, `client_id`, тип токена, организация и наборы инструментов из флагов `connect` (наборы перезаписываются при каждом запуске), а с `--allow-write` или `--allow-destructive` — и уровень доступа.
5. **Конфигурация клиента.** `connect` показывает, что именно будет записано, и спрашивает подтверждение; при отказе (или без ответа) конфигурация не меняется, а токен и профиль остаются.
   - **Claude Code** — через его CLI: `claude mcp add --scope <scope> <имя> -- <путь> serve --profile <профиль> …`. Файлы Claude Code напрямую не правятся. Если сервер с таким именем уже есть и запускает `wiki-mcp`, он заменяется (`claude mcp remove` и снова `add`) после подтверждения.
   - **Codex** — таблица `[mcp_servers.<имя>]` в `$CODEX_HOME/config.toml` (по умолчанию `~/.codex/config.toml`):

     ```toml
     [mcp_servers.wiki]
     command = "/opt/homebrew/bin/wiki-mcp"
     args = ["serve", "--profile", "codex"]
     ```

     Остальные записи, комментарии и форматирование файла сохраняются; запись с тем же именем заменяется на месте.

   Запись с тем же именем, которая запускает другой сервер, а не `wiki-mcp`, заменяется только после явного ответа в терминале; с `--yes` она не заменяется никогда. Чтобы подключить сервер рядом с ней, выберите другое имя через `--name`.

После подключения перезапустите клиент. В конфигурацию записывается абсолютный путь к запущенному бинарнику без раскрытия symlink: при установке через Homebrew путь `bin/wiki-mcp` переживает обновления.

Ссылки открываются в браузере по умолчанию. Браузер не открывается с `--no-browser`, по SSH и в Linux без графической сессии; ссылки печатаются всегда, их можно открыть на своём компьютере.

Для каждого клиента используйте отдельный профиль и отдельное OAuth-приложение, чтобы токен каждого можно было отозвать независимо.

## serve

```text
wiki-mcp serve [--profile <имя>] [--allow-write] [--allow-destructive]
               [--toolsets <набор,...>|all] [--dynamic-toolsets]
               [--tools-file <путь>]... [--allow-path <каталог>]...
               [--timeout <секунды>] [--max-response-bytes <байты>]
               [--log-level <уровень>] [--status]
```

Запускает MCP-сервер через stdio: MCP-клиент (Claude Code, Codex и другие) запускает команду сам и общается с ней через stdin и stdout. HTTP-режим описан ниже, в [`serve --http`](#serve---http). Каждая операция Wiki API из встроенной спецификации — отдельный инструмент; имя инструмента — короткое имя операции (`get_page`, `create_page`, `list_attachments`). Кроме них доступны составные инструменты `upload_attachment` и `wait_for_operation` и всегда — `api_search` (поиск по всем операциям) и `api_request` (запрос к любому пути API в пределах уровня доступа), см. [MCP-инструменты](tools.md).

Токен, организация и права берутся только из профиля (`--profile`, по умолчанию `default`): токен — из системного хранилища, его тип и организация — из `profiles.toml`. Профиль с IAM-токенами из `yc` или по ключу сервисного аккаунта получает токен сам перед первым запросом и обновляет его до истечения срока, поэтому сервер работает дольше 12 часов без перезапуска ([IAM-токены](iam.md)). Если чего-то нет, сервер не запускается и подсказывает команду `auth login`. В аргументах инструментов токена нет.

| Флаг | Назначение |
| --- | --- |
| `--profile <имя>` | Профиль с токеном и организацией. |
| `--allow-write` | Сузить права профиля до записи (профиль должен её разрешать). |
| `--allow-destructive` | Сузить права до удаления и изменения прав доступа (профиль должен их разрешать). |
| `--toolsets <набор,...>` | Наборы инструментов через запятую или `all`. С `--dynamic-toolsets` — наборы, включённые при запуске. |
| `--dynamic-toolsets` | [Динамические наборы](tools.md#динамические-наборы): при запуске только `api_search`, `api_request`, `list_toolsets`, `enable_toolset`, `disable_toolset` и пользовательские инструменты; наборы агент включает сам. Нужен клиент, который перечитывает список инструментов по уведомлению. Не сочетается с `--http`. |
| `--tools-file <путь>` | Дополнительный файл [пользовательских инструментов](tools.md#пользовательские-инструменты) в формате `tools.toml`; флаг повторяется. В HTTP-режиме читаются только эти файлы. |
| `--allow-path <каталог>` | Оставить из каталогов `allow_path` профиля только этот (он должен лежать внутри каталога профиля); флаг повторяется. |
| `--timeout <секунды>` | Таймаут одного запроса к API, по умолчанию 60. |
| `--max-response-bytes <байты>` | Предел ответа API, который возвращается агенту, по умолчанию 262144 (256 КиБ). Больший ответ — ошибка с подсказкой сузить запрос. С [фильтром `jq`](tools.md#фильтр-ответа-jq) предел относится к результату фильтра. На скачивание файлов в `save_to` не распространяется. |
| `--log-level <уровень>` | Уровень или фильтр логов в stderr (`info`, `debug`, `wiki_mcp_core=debug`). Без флага — переменная `RUST_LOG`, без неё — `warn`. |
| `--status` | Показать действующие настройки и выйти, не запуская сервер. |

### Уровни доступа и наборы

Уровень доступа и каталоги — из [прав профиля](#права-профиля); без них сервер работает только на чтение. Флаги `--allow-write`, `--allow-destructive` и `--allow-path` права только сужают: флаг сверх прав профиля — ошибка запуска, а на macOS права сверх одобренных отсекаются с предупреждением в stderr, и сервер запускается. Поэтому регистрации старых версий с флагами доступа продолжают запускаться. Наборы — из `--toolsets`, без флага — из `toolsets` профиля, иначе `pages`, `attachments`, `comments` и `grids`. Наборы `access` (персональные права доступа к страницам) и `extra` (операции, которых нет в справочнике Wiki API) включаются только явно. Неизвестный набор — ошибка запуска со списком допустимых. `--dynamic-toolsets` задаётся только флагом: в профиле такой настройки нет.

Пользовательские инструменты читаются при запуске из `tools.toml` рядом с `profiles.toml`, если файл есть, и из файлов `--tools-file`. Ошибка в файле — ошибка запуска; проверить файлы заранее можно командой [`tools check`](#tools).

Что входит в уровни и наборы, как устроены аргументы и ответы инструментов, `api_search` и `api_request` — в [MCP-инструментах](tools.md). Вырезание учётных данных из ответов и правила для локальных файлов — в [Безопасности](security.md).

### serve --status

```text
wiki-mcp serve --status [--profile <имя>] [--allow-write] [--allow-destructive] [--toolsets ...]
                        [--dynamic-toolsets] [--tools-file <путь>]... [--allow-path ...]
```

Печатает, с какими настройками запустился бы сервер с теми же флагами: профиль, сохранён ли токен (без значения) или откуда берутся IAM-токены (команда `yc`, ID ключа и сервисного аккаунта), тип токена, организацию, уровень доступа и откуда он взят (флаги, профиль или по умолчанию), состояние одобрения прав (macOS) и предупреждение, если права урезаны, включённые и выключенные наборы, включены ли динамические наборы, число инструментов, сколько пользовательских инструментов определено и зарегистрировано (и путь к `tools.toml`), разрешённые каталоги и путь к `profiles.toml`. Сервер не запускается, к API запросов нет. Если не хватает токена или организации, команда подсказывает, как их сохранить.

### serve --http

```text
wiki-mcp serve --http [--listen <IP:порт>] [--allowed-host <имя>]... [--allowed-origin <origin>]...
                      [--org-id <ID> | --cloud-org-id <ID>] [--max-request-bytes <байты>]
                      [--allow-write] [--allow-destructive] [--toolsets <набор,...>|all]
                      [--tools-file <путь>]... [--timeout <секунды>] [--max-response-bytes <байты>] [--log-level <уровень>]
```

Запускает тот же сервер как HTTP-сервис (Streamable HTTP без сессий): `POST /mcp` и `GET /health`, по умолчанию на `127.0.0.1:8767`. Профилей и системного хранилища в этом режиме нет: каждый запрос агента несёт токен в `Authorization: OAuth <токен>` (или `Bearer <IAM-токен>`) и организацию в `X-Org-Id` или `X-Cloud-Org-Id`, если её не задаёт флаг сервера. Уровень доступа (`--allow-write`, `--allow-destructive`), наборы и пользовательские инструменты (`--tools-file`) задаются только флагами: [права профиля](#права-профиля) и их одобрение на macOS относятся только к stdio. Локальные файлы выключены; `--profile`, `--allow-path`, `--status` и `--dynamic-toolsets` вместе с `--http` — ошибка.

| Флаг | Назначение |
| --- | --- |
| `--http` | Режим HTTP вместо stdio. |
| `--listen <IP:порт>` | Адрес и порт, по умолчанию `127.0.0.1:8767`. |
| `--allowed-host <имя>` | Дополнительное допустимое значение `Host` (`имя` или `имя:порт`); флаг повторяется. |
| `--allowed-origin <origin>` | Допустимый `Origin` браузерного клиента; флаг повторяется. |
| `--org-id <ID>` | Организация Yandex 360 для всех запросов; другая организация в запросе отклоняется. |
| `--cloud-org-id <ID>` | Организация Yandex Cloud для всех запросов; другая организация в запросе отклоняется. |
| `--max-request-bytes <байты>` | Предел тела запроса MCP, по умолчанию 1048576 (1 МиБ). |

Коды ответов, Docker-образ, `compose.yaml` и подключение клиентов — в [HTTP-режиме](http.md).

## auth

### auth login

```text
wiki-mcp auth login [--profile <имя>] [--org-id <ID> | --cloud-org-id <ID>]
                    [--token-type <oauth|iam>] [--token-stdin] [--skip-check]
                    [--iam-source <token|yc|service-account-key>]
                    [--service-account-key <файл>] [--yc-path <путь>] [--yc-profile <имя>]
```

Сохраняет токен Wiki и организацию профиля или настраивает профиль на IAM-токены из источника:

1. Организация: `--org-id` (Yandex 360) или `--cloud-org-id` (Yandex Cloud); без флагов берётся из профиля, а если её там нет — спрашивается тип и ID.
2. Тип токена: `--token-type oauth` (OAuth-токен, по умолчанию) или `--token-type iam` (IAM-токен Yandex Cloud); без флага — тип из профиля, иначе `oauth`. Источник IAM-токенов: `--iam-source token` (вставленный токен), `--iam-source yc` или `--iam-source service-account-key`; флаги источника подразумевают `--token-type iam`, без них — источник из профиля. `--service-account-key <файл>` подразумевает `--iam-source service-account-key`, `--yc-path` и `--yc-profile` — `--iam-source yc`.
3. Токен: скрытым вводом в терминале или, с `--token-stdin`, из stdin (например, из менеджера паролей). С `--token-stdin` организация не спрашивается: передайте флаг, если в профиле её ещё нет.
4. Проверка: запрос `GET /v1/users/me` с токеном и заголовком организации; печатается пользователь. `--skip-check` пропускает проверку (без сети).
5. Токен сохраняется в системное хранилище (заменяя прежний), тип токена и организация — в `profiles.toml`. Остальные настройки профиля не меняются; новый профиль создаётся с доступом только на чтение.

OAuth-токен выдаёт ваше собственное OAuth-приложение Яндекса с доступом к Wiki. Если в профиле есть `client_id`, команда печатает ссылку для получения токена; создать приложение и сохранить `client_id` помогает [`connect`](#connect). Для вставленного IAM-токена команда подсказывает `yc iam create-token`: такой токен живёт не больше 12 часов, после этого его нужно сохранить заново.

С `--iam-source yc` или `--service-account-key <файл>` токен не вводится и не сохраняется: организация — только Yandex Cloud, команда получает токен из источника и проверяет его запросом `GET /v1/users/me`, в профиль пишутся тип, источник и настройки `yc`, а ключ сервисного аккаунта — в системное хранилище (путь к файлу не сохраняется). Без `--service-account-key` профиль с ключом берёт сохранённый ключ. `--token-stdin` с этими источниками — ошибка. Подробности — в [IAM-токенах](iam.md).

### auth status

```text
wiki-mcp auth status [--profile <имя>] [--skip-check]
```

Показывает профиль, сохранён ли токен (без значения), тип токена, источник IAM-токенов (команда `yc` или ID ключа и сервисного аккаунта; с проверкой токен получается из источника и сразу забывается), организацию, пользователя, которому принадлежит токен, и организацию из ответа Wiki (запрос `GET /v1/users/me`; `--skip-check` — без запроса), `client_id`, клиент, в котором профиль зарегистрирован через `connect`, разрешены ли запись и удаление, наборы инструментов и путь к `profiles.toml`. Если проверка не прошла, причина печатается в строке `User`.

### auth logout

```text
wiki-mcp auth logout [--profile <имя>] [--forget]
```

Удаляет токен и ключ сервисного аккаунта профиля из системного хранилища. С `--forget` также удаляет настройки профиля из `profiles.toml`. Если токен больше нигде не нужен, отзовите его ([отзыв токена](oauth.md#отзыв-токена)); ненужный ключ сервисного аккаунта удалите в Yandex Cloud (`yc iam key delete`).

## call

```text
wiki-mcp call [--profile <имя>] [--allow-write] [--allow-destructive]
              [--allow-path <каталог>]... [--toolsets <набор,...>] [--tools-file <путь>]...
              [--timeout <секунды>] [--max-response-bytes <байты>]
              [<инструмент> [<имя>=<значение> | <имя>:=<JSON>]... [--args <JSON>|-] [--schema] [--yes] [--raw]]
```

Вызывает инструмент сервера из консоли.

- Без инструмента печатает инструменты, доступные профилю, с уровнем доступа и первой строкой описания. `--schema` печатает схему аргументов инструмента.
- Сервер собирается как в `serve` без флагов: токен, организация и [права профиля](#права-профиля) (на macOS — одобренные), флаги только сужают. По умолчанию включены все наборы (`--toolsets` сужает), динамических наборов нет. MCP-клиент работает в этом же процессе, поэтому проверка аргументов, уровни доступа, фильтр `jq` и вырезание учётных данных те же, что у агента.
- Аргументы: `имя=значение` — тип берётся из схемы инструмента (числа, логические значения, JSON-массивы и объекты; для массива строк — список через запятую), `имя:=JSON` — всегда JSON, `--args` — все аргументы одним JSON-объектом (`-` — из stdin). Флаги команды пишутся до имени инструмента.
- Инструменты уровня удаления спрашивают подтверждение в терминале; `--yes` — без вопроса, без терминала вызов отклоняется.
- Результат: текстовые блоки (JSON — с отступами); `--raw` — результат MCP целиком. Код выхода — 0, если инструмент выполнился, и 1, если он вернул ошибку (`isError`) или вызов не удался.

```bash
wiki-mcp call get_current_user
wiki-mcp call get_page slug=users/name/page fields=content
wiki-mcp call api_request method=GET path=/v1/users/me jq='.username'
wiki-mcp call --profile codex list_page_descendants --args '{"slug": "team/project"}'
```

## ui

```text
wiki-mcp ui
```

Интерактивный просмотр профилей в терминале. Вкладки:

- **Profile** — настройки профиля и состояние токена: сохранён ли он (сам токен не показывается) или откуда берутся IAM-токены, тип токена, организация, OAuth-приложение (`client_id`), наборы, клиент из `connect`.
- **Access** — права профиля и их одобрение. `r`, `w`, `d` — уровень, `a` — добавить каталог, `x` — убрать, `u` — отменить, `s` — сохранить. На macOS сохранение прав шире одобренных спрашивает Touch ID или пароль пользователя macOS.
- **Clients** — регистрации сервера в Claude Code (`~/.claude.json`, `.mcp.json` текущего каталога) и Codex (`$CODEX_HOME/config.toml`): профиль, флаги и расхождения с правами профиля. `f` регистрирует запись заново без флагов доступа (остальные аргументы записи сохраняются). Значения переменных окружения записей не читаются.
- **Account** — что видно токену в Wiki (`c` — проверить): организация, источник токена, пользователь токена и организация из ответа `GET /v1/users/me`. Права самого токена (`wiki:read`, `wiki:write`) Wiki не сообщает: их видно в настройках OAuth-приложения или роли аккаунта Yandex Cloud.
- **Tools** — инструменты, которые профиль даёт агенту (`c` — загрузить), `Enter` — вызвать с аргументами `имя=значение`, `?` — схема.

`q` или `Esc` — выход, `Tab` и `1`–`5` — вкладки, `F5` — перечитать. Без терминала (агент, CI) команда завершается ошибкой.

## tools

```text
wiki-mcp tools list [--tools-file <путь>]...
wiki-mcp tools check [--tools-file <путь>]...
```

Работают с [пользовательскими инструментами](tools.md#пользовательские-инструменты). Файл пользователя `tools.toml` рядом с `profiles.toml` читается всегда, если он есть; `--tools-file` добавляет те же файлы, что и у `serve`. К API команды не обращаются, токен не нужен.

- `tools list` печатает таблицу: имя, уровень доступа, операция, фиксированные аргументы, есть ли фильтр `jq`, файл. Инструменты выше уровня доступа профиля сервера при запуске не регистрируются.
- `tools check` проверяет файлы так же, как `serve` при запуске (TOML, поля, операции, фиксированные аргументы по схеме операции, фильтры `jq`, совпадения имён), и печатает для каждого файла `OK` и число инструментов. Ошибка — код выхода не 0 и сообщение с файлом и инструментом.

## Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `WIKI_MCP_CONFIG_DIR` | Каталог с `profiles.toml` и `tools.toml` вместо `~/.config/wiki-mcp`. |
| `CODEX_HOME` | Каталог конфигурации Codex для `connect codex` вместо `~/.codex`. |
| `RUST_LOG` | Уровень логов `serve` в stderr, если не задан `--log-level`. |

Токен Wiki и ключ сервисного аккаунта из переменных окружения не читаются никогда.
