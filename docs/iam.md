# IAM-токены: федеративные и сервисные аккаунты

Обычный пользователь работает с Wiki через [OAuth-токен](oauth.md). Федеративные аккаунты (вход через SSO организации Yandex Cloud) и сервисные аккаунты Yandex Cloud OAuth-токен Яндекса не получают: Wiki принимает от них IAM-токен Yandex Cloud в заголовке `Authorization: Bearer <IAM-токен>`.

IAM-токен живёт не больше 12 часов. Чтобы агент работал дольше без ручного обновления, профиль может получать IAM-токены сам и обновлять их до истечения срока. Источник токенов задаётся при настройке профиля (`iam_source` в `profiles.toml`):

| Источник | Флаг | Откуда токен | Что хранится |
| --- | --- | --- | --- |
| `yc` | `--iam-source yc` | Команда `yc iam create-token` | Ничего: учётные данные остаются в конфигурации `yc`. |
| `service-account-key` | `--service-account-key <файл>` | Обмен JWT, подписанного авторизованным ключом сервисного аккаунта, в IAM API Yandex Cloud | Ключ — в системном хранилище. |
| `token` | `--token-type iam` | Токен, который вы вставили сами | Токен — в системном хранилище; через 12 часов его нужно сохранить заново. |

Полученные токены держатся только в памяти процесса: они не пишутся в файлы и хранилище и не печатаются.

## Когда нужен IAM

- **Федеративный аккаунт** — пользователь входит в организацию Yandex Cloud через SSO своей компании (федерация удостоверений) и не имеет аккаунта Яндекс ID для OAuth. Подходит источник `yc`.
- **Сервисный аккаунт** — робот без человека: CI, автоматизация, общий агент. Подходит ключ сервисного аккаунта (на машине не нужен `yc`) или `yc` с профилем сервисного аккаунта. Сервисный аккаунт работает с Wiki как отдельный пользователь со своими правами на страницы.

Источники `yc` и `service-account-key` работают только с организацией Yandex Cloud (заголовок `X-Cloud-Org-Id`). Профиль с таким источником и организацией Yandex 360 (`X-Org-Id`) не запускается.

## Ключ сервисного аккаунта

Создайте авторизованный ключ сервисного аккаунта в [Yandex Cloud CLI](https://yandex.cloud/ru/docs/cli/quickstart) или в консоли Yandex Cloud:

```bash
yc iam key create --service-account-name <имя> --output key.json
```

Сохраните ключ в профиль:

```bash
wiki-mcp auth login --profile robot --service-account-key key.json --cloud-org-id <ID организации>
```

Команда читает файл, получает IAM-токен по ключу и проверяет его запросом `GET /v1/users/me`; печатается пользователь. Ключ сохраняется в системное хранилище: сервис `dev.filipov.wiki-mcp`, учётная запись `<профиль>:service-account-key`. Путь к файлу нигде не сохраняется, поэтому после команды файл `wiki-mcp` больше не нужен: удалите его или храните там, где к нему нет доступа у агента. Ключ из хранилища не печатает ни одна команда.

Как сервер получает токен по ключу:

1. Подписывает ключом JWT (алгоритм PS256, `kid` — ID ключа, `iss` — ID сервисного аккаунта, `aud` — `https://iam.api.cloud.yandex.net/iam/v1/tokens`, срок — 10 минут).
2. Отправляет его запросом `POST https://iam.api.cloud.yandex.net/iam/v1/tokens` и получает IAM-токен и срок его действия. Редиректы не выполняются: JWT уходит только на этот адрес.

Ключ сервисного аккаунта — долгоживущий секрет. Если он мог утечь, удалите его в Yandex Cloud (`yc iam key delete <ID ключа>`) и сохраните новый. Заменить ключ в профиле — та же команда `auth login` с новым файлом.

## Источник `yc`

Нужен Yandex Cloud CLI (`yc`). `wiki-mcp` ищет его в `PATH` или берёт абсолютный путь из `--yc-path`. Учётные данные остаются в конфигурации `yc` (`~/.config/yandex-cloud`), `wiki-mcp` их не читает и не копирует.

Федеративный аккаунт:

```bash
yc init --federation-id <ID федерации>
yc iam create-token        # проверка: печатает токен, при первом запуске откроет браузер для входа
```

Сервисный аккаунт через отдельный профиль `yc`:

```bash
yc iam key create --service-account-name <имя> --output key.json
yc config profile create wiki-sa
yc config set service-account-key key.json
yc iam create-token --profile wiki-sa
```

Если команда `yc iam create-token` (с `--profile`, если нужен) печатает токен, `wiki-mcp` сможет его получить. Сам токен никуда не копируйте.

```bash
wiki-mcp auth login --profile fed --iam-source yc --cloud-org-id <ID организации> [--yc-profile <профиль yc>] [--yc-path <путь к yc>]
```

`--yc-profile` и `--yc-path` подразумевают `--iam-source yc`. `yc` запускается без оболочки, со списком аргументов `iam create-token [--profile <профиль>] --format json`, закрытым stdin и таймаутом 60 секунд (в `auth login` и `connect` — 3 минуты: для федеративного аккаунта `yc` может открыть браузер для входа); по таймауту процесс останавливается. Системное хранилище профилю с `yc` не нужно: такой профиль работает и на Linux-сервере без Secret Service.

## Подключение

Профиль настраивают `auth login` (примеры выше) или `connect`:

```bash
wiki-mcp connect codex --service-account-key key.json --cloud-org-id <ID организации>
wiki-mcp connect claude-code --iam-source yc --cloud-org-id <ID организации> [--yc-profile <профиль yc>]
```

`connect` с этими флагами не создаёт OAuth-приложение и не спрашивает токен: он сохраняет профиль, проверяет, что источник выдаёт токен, который принимает Wiki, и записывает сервер в конфигурацию клиента. Если источник или проверка не прошли, ничего не сохраняется. `--skip-check` сохраняет профиль без получения токена и без запроса к API.

В `profiles.toml` записываются тип токена, источник, организация и настройки `yc`, но не токен и не ключ:

```toml
[profiles.robot]
token_type = "iam"
iam_source = "service-account-key"   # или "yc"
yc_profile = "wiki-sa"               # только для yc, необязательно: без него — активный профиль yc
yc_path = "/opt/yc/bin/yc"           # только для yc, необязательно: без него — yc из PATH
allow_write = false
allow_destructive = false
toolsets = []

[profiles.robot.org]
type = "cloud"
id = "<ID организации>"
```

Повторные `auth login` и `connect` для такого профиля остаются на том же источнике и без флагов; `auth login` без `--service-account-key` берёт сохранённый ключ. Вернуть профиль на OAuth: `wiki-mcp auth login --profile <профиль> --token-type oauth`. Прежние профили (`token_type = "oauth"` или `"iam"` без `iam_source`) работают как раньше: поле `iam_source` у них не появляется.

`auth status` и `serve --status` показывают источник: команду `yc` или ID ключа и сервисного аккаунта (они не секретные). `auth status` вдобавок получает токен и показывает пользователя (`--skip-check` — без получения токена и без запроса). `auth logout` удаляет из хранилища и токен, и ключ сервисного аккаунта профиля.

## Как сервер обновляет токен

- Токен запрашивается перед первым запросом к API и заменяется не реже раза в час, а если источник сообщил срок (`expires_at`), то и за 10 минут до его истечения. Сервер работает сколько угодно дольше 12 часов без перезапуска.
- Если Wiki ответила `401`, сервер один раз получает новый токен и повторяет запрос. Если источник выдал тот же токен, повтора нет: дело не в сроке. Запросы `POST` и `PATCH` повторяются, только если `401` пришёл на сам запрос, а не после редиректа: `401` Wiki возвращает до выполнения операции, поэтому повтор не создаст страницу или комментарий дважды.
- Одновременно идёт не больше одного получения токена: остальные запросы ждут и получают тот же токен.
- Токены из источника вырезаются из текстов ошибок, если Wiki их отразила; stderr `yc` и сообщение IAM API попадают в ошибку только короткой выжимкой с замаскированными длинными значениями.

## Ограничения

- Источник должен работать на машине, где запущен сервер: `yc` установлен и настроен, IAM API Yandex Cloud доступен по сети. Если токен получить не удалось, запрос к Wiki не отправляется, а агент получает ошибку с источником, который нужно проверить (`wiki-mcp auth status`).
- Токен не переживает перезапуск сервера: после запуска он запрашивается снова.
- `yc` берёт учётные данные из своей конфигурации и переменных окружения. Их защита — на стороне `yc` и пользователя.
- В [HTTP-режиме](http.md) сервер IAM-токены не получает и не обновляет: агент сам передаёт `Authorization: Bearer <IAM-токен>` в каждом запросе, а когда токен истечёт, Wiki ответит `401` и токен в конфигурации клиента нужно заменить.

Ошибки получения IAM-токена и `401` с IAM разобраны в [решении проблем](troubleshooting.md#iam-токен-не-получен).
