# Решение проблем

Ошибки HTTP-режима (`401`, `400 missing_organization`, `403` по `Host` и `Origin` и другие) описаны в [HTTP-режиме](http.md#проблемы).

## Homebrew не ставит формулу из стороннего tap

Устанавливайте по полному имени, а tap добавляйте с полным адресом: он размещён на SourceCraft, а не на GitHub.

```bash
brew tap filipov-dev/tap https://git.sourcecraft.dev/filipov-dev/homebrew-tap.git
brew install filipov-dev/tap/wiki-mcp
```

## macOS: Keychain спрашивает разрешение

macOS может спросить, разрешить ли `wiki-mcp` доступ к записи `dev.filipov.wiki-mcp` в связке ключей, — обычно когда токен сохранила одна сборка бинарника, а читает другая. Нажмите «Всегда разрешать», иначе вопрос будет повторяться при каждом запуске сервера.

Бинарник из Homebrew и релизных архивов подписан Developer ID, поэтому после обновления разрешение, как правило, сохраняется. Бинарник, собранный из исходников, не подписан: после каждой пересборки macOS считает его новой программой и спрашивает снова.

Когда сервер запускает MCP-клиент, окно с вопросом появляется поверх других окон, а клиент ждёт ответа. Если клиент пишет, что сервер не запустился или не ответил, проверьте, нет ли такого окна.

## Linux: Secret Service недоступен

В Linux токен хранится через Secret Service (D-Bus); `libdbus-1` не нужна. Ошибка `no Secret Service (org.freedesktop.secrets) is available …` при `connect`, `auth` или `serve` означает одно из:

- в сессии не запущен провайдер Secret Service — GNOME Keyring, KeePassXC (с включённой интеграцией Secret Service), KWallet и т. п.;
- нет сессионной шины D-Bus: например, при входе по SSH на сервер без графической сессии;
- связка ключей заблокирована и разблокировать её некому.

Запасного файлового хранилища нет, и хранить токен в переменной окружения или файле нельзя — это намеренное ограничение. Варианты:

- запустить провайдер вручную ([Linux без Secret Service](cli.md#linux-без-secret-service): `dbus-run-session` и `gnome-keyring-daemon --unlock`);
- запустить `wiki-mcp` на рабочей машине с графической сессией;
- использовать [HTTP-режим](http.md): там хранилище не нужно, токен передаёт агент в заголовке запроса.

## Linux: ошибка проверки сертификата

Сертификат Wiki API проверяется по корневым сертификатам системы. Если запросы к API падают с ошибкой TLS или сертификата, проверьте, что они установлены: в минимальных образах (Debian/Ubuntu slim и т. п.) их нет: поставьте пакет `ca-certificates` или укажите файл сертификатов в переменной `SSL_CERT_FILE`.

## Работа по SSH

- `connect` и `auth login` по SSH не открывают браузер (как и в Linux без графической сессии и с `--no-browser`): ссылки на создание приложения и получение токена печатаются, откройте их на своём компьютере, а токен вставьте в терминал.
- В Linux по SSH обычно нет сессии D-Bus и Secret Service — см. [выше](#linux-secret-service-недоступен).
- В macOS по SSH связка ключей входа может быть заблокирована: разблокируйте её (`security unlock-keychain`) или выполните `connect` в обычном сеансе.
- В Windows Credential Manager есть только в сеансе, вошедшем с паролем: в SSH-сеансе со входом по ключу, в службе или задаче планировщика без сохранённого пароля `auth` и `serve` падают с ошибкой «A specified logon session does not exist». Выполните `connect` и запускайте MCP-клиент в обычном сеансе пользователя ([Windows](clients.md#windows)) или используйте [HTTP-режим](http.md).

## «no Wiki token is stored for profile …»

Для профиля из `serve --profile` нет токена в системном хранилище. Проверьте имя профиля в конфигурации клиента и сохраните токен:

```bash
wiki-mcp auth status --profile <профиль>
wiki-mcp auth login --profile <профиль>
```

Профиль по умолчанию для `serve` и `auth` — `default`, а `connect` по умолчанию создаёт профиль с именем клиента (`claude-code`, `codex`). `wiki-mcp serve --status --profile <профиль>` покажет, чего не хватает для запуска: токена или организации.

## Wiki отклонил токен: HTTP 401

`connect`, `auth login` или `auth status` пишут `Wiki rejected the token (HTTP 401)`, либо инструмент возвращает ошибку с кодом `401`. Токен скопирован не полностью, истёк или отозван; IAM-токен живёт не больше 12 часов. Ещё одна причина — неверный тип токена: OAuth-токен, сохранённый как `--token-type iam`, отправляется со схемой `Bearer` и отклоняется. Профиль, который сам получает IAM-токены (`yc` или ключ сервисного аккаунта), при `401` один раз получает новый токен и повторяет запрос; если `401` остаётся, у пользователя токена нет доступа к Wiki организации — проверьте организацию и права аккаунта. Для OAuth-токена получите новый по ссылке приложения ([получение токена](oauth.md#получение-токена)) и замените сохранённый:

```bash
wiki-mcp auth login --profile <профиль>
```

Сервер читает токен из хранилища при запуске, поэтому после замены перезапустите его: переподключите сервер в клиенте (`/mcp` в Claude Code) или перезапустите клиент.

## IAM-токен не получен

Агент получает ошибку `the server could not get a Yandex Cloud IAM token, so the request was not sent`, а `auth login`, `connect` или `auth status` — `cannot get an IAM token`. Запрос к Wiki в этом случае не отправляется. Проверьте источник профиля (`wiki-mcp auth status --profile <профиль>` покажет его):

- **`yc` не найден.** Установите Yandex Cloud CLI или укажите абсолютный путь: `wiki-mcp auth login --profile <профиль> --yc-path <путь к yc>`. Клиент MCP может запускать сервер с другим `PATH`, чем у вашей оболочки, поэтому абсолютный путь надёжнее.
- **`yc` завершился с ошибкой.** В ошибке — короткая выжимка его stderr. Выполните `yc iam create-token` (с `--profile`, если он задан в профиле) сами: федеративному аккаунту может понадобиться войти заново в браузере, сервисному — проверить ключ в конфигурации `yc`. Вывод команды — токен: не копируйте его никуда.
- **`yc` не ответил за 60 секунд.** Обычно `yc` ждёт входа в браузере. Войдите через `yc iam create-token` в терминале, затем повторите запрос.
- **IAM API отклонил ключ сервисного аккаунта.** Ключ удалён или сервисный аккаунт удалён или заблокирован. Создайте новый ключ (`yc iam key create --service-account-name <имя> --output key.json`) и сохраните его: `wiki-mcp auth login --profile <профиль> --service-account-key key.json`.
- **IAM API недоступен.** Сервер ходит в `https://iam.api.cloud.yandex.net`; проверьте сеть и прокси машины, где запущен сервер.
- **«no service account key is stored for profile …».** Ключа нет в системном хранилище (например, после `auth logout`): сохраните его снова с `--service-account-key <файл>`.

После исправления сервер перезапускать не нужно: следующий запрос снова попробует получить токен. Подробности — в [IAM-токенах](iam.md).

## Нет доступа: HTTP 403

`Wiki denied access (HTTP 403)` при проверке токена или ошибка `403` у инструмента:

- **Неверная организация.** ID или тип организации не совпадает с той, к которой у пользователя есть доступ: Yandex 360 для бизнеса — `X-Org-Id`, Yandex Cloud Organization — `X-Cloud-Org-Id`. Если `403` приходит на любую страницу, дело почти наверняка в организации. Исправьте: `wiki-mcp auth login --profile <профиль> --org-id <ID>` (или `--cloud-org-id <ID>`).
- **Нет прав у пользователя.** Пользователь токена не видит страницу или не может её менять. Права выдаёт владелец страницы или администратор Wiki.
- **Нет прав у токена.** Запись токеном приложения только с `wiki:read`. Добавьте приложению `wiki:write` и получите новый токен ([права приложения](oauth.md#права-приложения)).

## Страница не найдена: HTTP 404

Чаще всего slug неполный. Slug — путь страницы от корня Wiki без домена: `team/project/page`, а не `project/page` и не полный URL. Возьмите его из адреса страницы в браузере или из поля `slug` ответа `get_page_by_id`. Если id страницы известен, работайте по `idx`: так надёжнее. Новая страница создаётся по тому `slug`, который передан: чтобы она оказалась под родителем, укажите полный путь.

## Агенту не хватает инструмента

- Инструмент записи или удаления не зарегистрирован: профиль сервера разрешает только чтение. Вызов по имени возвращает ошибку с нужным уровнем. Разрешите запись или удаление профилю в `wiki-mcp ui` (вкладка Access) или повторным `connect … --allow-write` и перезапустите клиент ([права профиля](cli.md#права-профиля)).
- На macOS в профиле запись разрешена, а сервер работает только на чтение и пишет в stderr, что права не одобрены (`serve --status` показывает строку `Approval`): права сверх чтения действуют только после одобрения владельцем. Откройте `wiki-mcp ui`, вкладку Access, и сохраните права (`s`): система спросит Touch ID или пароль. Так же нужно один раз одобрить права профилей, которые прежние версии сохранили без одобрения.
- Инструмент из выключенного набора (`access`, `extra`): агент найдёт его через `api_search`, в ответе сказано, каким `--toolsets` его включить. Вызвать операцию в пределах уровня доступа можно и через `api_request`.
- Инструментов с локальными файлами нет в HTTP-режиме: там локальные файлы выключены. Файл туда загружается через `create_upload_url` (нужен `--allow-write`) и `curl` ([загрузка файлов](http.md#загрузка-файлов)); скачивания нет.

## Клиент не видит сервер или его инструменты

- Перезапустите клиент после `connect` или правки конфигурации.
- Укажите в конфигурации клиента абсолютный путь к бинарнику (`command -v wiki-mcp`).
- Запустите команду из конфигурации вручную, например `wiki-mcp serve --profile codex`. Ошибки запуска (нет токена, нет организации, неизвестный набор, несуществующий каталог в `allow_path` профиля, флаг доступа сверх прав профиля) печатаются в stderr. Если ошибок нет, сервер ждёт сообщений MCP на stdin — остановите его `Ctrl-C`.
- Для подробных логов добавьте в аргументы сервера `--log-level debug`. Логи пишутся в stderr.

## Файл «is outside the allowed directories»

Инструменты работают с локальными файлами только в рабочем каталоге сервера, системном временном каталоге и каталогах `allow_path` профиля. Если клиент запускает сервер в домашнем каталоге или в `/`, рабочий каталог не разрешён. Добавьте нужный каталог в профиль: `wiki-mcp ui`, вкладка Access, клавиша `a`, или `allow_path = ["/path/to/project"]` в `profiles.toml` ([Безопасность](security.md#локальные-файлы)).

## Ошибка «asks for … access, but the profile allows only …»

Флаг `--allow-write`, `--allow-destructive` или `--allow-path` в команде запуска просит больше, чем разрешает профиль: флаги только сужают права профиля. Разрешите нужный уровень или каталог в профиле (`wiki-mcp ui`) или уберите флаг из аргументов сервера (повторный `connect` перерегистрирует запись без флагов доступа). Это относится к stdio: в HTTP-режиме уровень задают сами флаги ([HTTP-режим](http.md#отличия-от-stdio)).

## Загрузка файла не удалась

- `upload_attachment` называет шаг, на котором произошла ошибка, и сообщает, отменена ли сессия загрузки. Ничего не прикрепляется, повторите вызов после исправления причины.
- Файл больше 16 МиБ загружается только в хранилища, которые принимают файл частями. Для остальных сессия отменяется с ошибкой: уменьшите файл или приложите его через интерфейс Wiki.
- Если загрузки обрывались на середине вручную (`create_upload_session` без `finish_upload_session`), незавершённые сессии занимают квоту: отмените их `abort_upload_session` или все сразу `abort_all_upload_sessions`.
- Файл прикреплён, но не виден в тексте страницы: вложение само в текст не попадает. Допишите `{% file src="<download_url>" name="<имя>" %}` через `append_page_content`.

## Ответ слишком большой

Ответ API больше `--max-response-bytes` (256 КиБ по умолчанию) возвращается ошибкой с подсказкой сузить запрос. Запросите только нужные блоки `fields` (текст страницы — `content`), уменьшите `page_size` или используйте [постраничную выдачу](tools.md#постраничная-выдача). Лимит можно увеличить флагом `--max-response-bytes` в аргументах сервера. Файлы скачивайте в `save_to`: на них лимит не распространяется.

## Ошибка 400 или «VALIDATION_ERROR»

Wiki отклонил аргументы. Проверьте схему инструмента (`api_search` с `tool_name`) и страницу справочника по ссылке в описании инструмента: тело запроса передаётся в `body`, `fields` — строка через запятую, `url` у `download_attachment_by_url` — без косой черты в начале.
