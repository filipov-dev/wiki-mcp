# OpenAPI для Yandex Wiki Public API

Wiki API сам отдаёт официальную спецификацию (OpenAPI 3.1): `https://api.wiki.yandex.net/v1/openapi.json`. В ней длинные имена операций, короткие английские названия, у большинства параметров нет описаний, нет заголовков авторизации, а уровень доступа по HTTP-методу не определить: `POST` в Wiki API означает и поиск, и правку. Поэтому инструменты генерируются из объединённой спецификации:

- `wiki.upstream.json` — снимок официальной спецификации. Хранится в репозитории, чтобы сборка не зависела от сети. Руками не правится.
- `overlay.json` — файл-дополнение: наборы инструментов, авторизация, описания и запись для каждой операции (`"<МЕТОД> <путь>"`).
- `build_openapi.py` — скрипт объединения (Python 3.10+, без сторонних пакетов и сети).
- `wiki.openapi.json` — результат объединения; его читает `build.rs`. Руками не правится.
- `spec_drift.py` — проверка, не отстал ли снимок от API и справочника (Python 3.10+, без сторонних пакетов; ходит в сеть), см. [ниже](#не-отстал-ли-снимок-от-api).

## Что внутри

57 операций: 47 описаны в [справочнике Wiki API](https://yandex.ru/support/wiki/ru/api-ref/about), 10 есть только в официальной спецификации.

| Набор | По умолчанию | Операций | read | write | destructive |
|---|---|---|---|---|---|
| `pages` — страницы, подстраницы, копирование, восстановление, поиск, текущий пользователь | включён | 15 | 9 | 5 | 1 |
| `attachments` — вложения и сессии загрузки файлов | включён | 11 | 4 | 6 | 1 |
| `comments` — комментарии | включён | 4 | 2 | 1 | 1 |
| `grids` — динамические таблицы | включён | 13 | 2 | 8 | 3 |
| `access` — персональные права доступа к страницам | выключен | 4 | 0 | 0 | 4 |
| `extra` — операции, которых нет в справочнике | выключен | 10 | 7 | 3 | 0 |

Уровни доступа (`x-access-level`):

- `read` — всё, что только читает, включая `POST /v1/search` (`search`) и `POST /v1/grids/{idx}/columns/suggest` (`suggest_grid_column`);
- `destructive` — удаление (страниц, вложений, комментариев, таблиц, строк и столбцов таблиц) и изменение прав доступа (весь набор `access`);
- `write` — остальное.

В наборе `extra`: `move_page`, `get_move_operation_status`, `list_page_revisions`, `list_page_backlinks`, `list_spaces`, `get_attachment`, `download_attachment_preview`, `suggest_grid_column`, `update_grid_column`, `update_grid_row`. В их описании сказано, что операции нет в справочнике, а `externalDocs` ведёт на обзор раздела. У остальных `externalDocs.url` — страница операции в справочнике.

Авторизация описана в `components.securitySchemes` (`OAuth`: `Authorization: OAuth <токен>`; `IamToken`: `Authorization: Bearer <IAM-токен>`) и верхнеуровневом `security`, организация — в `components.parameters` (`XOrgId` — `X-Org-Id`, `XCloudOrgId` — `X-Cloud-Org-Id`, нужен ровно один). В параметры операций эти заголовки не входят: их подставляет исполнитель, агент их не передаёт.

## Запись операции в дополнении

- `name` — имя MCP-инструмента; становится `operationId`. Исходный `operationId` сохраняется в `x-upstream-operation-id`.
- `toolset` — slug набора инструментов из списка `toolsets`; становится единственным тегом операции.
- `x-access-level` — `read`, `write` или `destructive`.
- `summary`, `description`, `externalDocs.url` — обязательны, скрипт падает без них.
- `parameter_descriptions` — описания параметров по имени (`{"slug": "..."}`); схема параметра остаётся из официальной спецификации. Общий словарь `parameter_descriptions` верхнего уровня (`idx`, `cursor`, `page_size`, `fields` и другие) действует на все операции, словарь операции его уточняет. Скрипт падает, если имени нет среди параметров операции или общее описание ни к чему не применилось.
- Любые другие поля операции OpenAPI (`parameters`, `requestBody`, `responses` и другие) заменяют поля официальной спецификации целиком.

Верхнеуровневые `info`, `servers`, `externalDocs` и `security` дополнения заменяют официальные. Общие компоненты дополнения (`components`) добавляются к официальным; совпадение имён — ошибка.

## Расхождения

Исправлено в дополнении:

- `POST /v1/pages/{idx}` (`update_page`) и `POST /v1/pages/{idx}/append-content` (`append_page_content`): в справочнике в теле есть строковое поле `revision` (версия, на которой основано изменение; при несовпадении — конфликт), в официальной схеме его нет. Тело заменено схемами `PageUpdateRequest` и `PageAppendContentRequest`: официальная схема через `allOf` и поле `revision`. Поле `actuality` у `update_page` есть в официальной схеме, но не в справочнике; оставлено.
- `PUT /v1/upload_sessions/{session_id}/upload_part` (`upload_file_part`): в официальной спецификации нет тела запроса, справочник требует байты части с `Content-Type: application/octet-stream`. Добавлено обязательное тело `application/octet-stream` со схемой `{"type": "string", "format": "binary"}`; параметры `session_id` и `part_number` остаются из официальной спецификации.
- Скачивание (`download_attachment_by_url`, `download_attachment`, `download_attachment_preview`): ответ `200` описан без содержимого и в официальной спецификации, и в справочнике, хотя операции отдают файл. Ответ описан как `application/octet-stream` (`format: binary`).
- `servers` в официальной спецификации пуст; указан `https://api.wiki.yandex.net`.
- 92 из 128 параметров официальной спецификации были без описания (в том числе `idx`, `cursor`, `fields`); описания взяты из справочника и добавлены через `parameter_descriptions`. Описания `order_by` в официальной спецификации ссылаются на несуществующий параметр `direction` (верно `order_direction`) — заменены.

Проверено запросами к настоящему Wiki API на тестовой странице и уточнено в описаниях операций:

- `download_attachment_by_url`: поле `download_url` в ответах начинается с косой черты, а параметр `url` принимает адрес только без неё.
- `append_page_content`: разделы нумеруются по порядку всех заголовков с 1, раздел заголовка первого уровня охватывает всю страницу под ним. На страницах нового редактора якоря не находятся ни в одном из проверенных видов (`{#имя}` в заголовке, `{{anchor}}`, HTML); работают `section`, `body` и `anchor` с `fallback=true`.
- `get_page` и `get_page_by_id`: страница с редиректом возвращается сама, цель — в блоке `redirect`; `raise_on_redirect=true` даёт 400 `REDIRECT_CHAIN` с `source_page` и `target_page` в `details`.
- `move_page`: пробный и настоящий запуск могут вернуть один id операции.
- `download_attachment_preview`: для файла без превью отдаётся картинка-заглушка.
- Разбивка через `cursor` у `list_page_descendants` ничего не теряет: проход по страницам даёт тот же список, что и один большой запрос.
- Скачивание вложения отдаёт файл сразу ответом 200, без перенаправления на внешнее хранилище.
- В теле ошибок Wiki кроме `error_code`, `debug_message` и `details` бывает поле `message` (у ошибок валидации — текст на языке пользователя).
- `fields` у страниц: API принимает только `redirect`, `breadcrumbs`, `actuality`, `attributes`, `content`, `access_policy`, `access_lists`, `owner`; `fields=last_revision_id` из справочника даёт 400 со списком допустимых. Id текущей версии — первая запись `list_page_revisions` (версии идут от новых к старым).
- `revision` в теле `update_page`: на wysiwyg-странице устаревший номер (строкой и числом) принимается без конфликта и правка записывается. Описания больше не обещают ошибку конфликта.
- `create_page`: `page_type` в теле игнорируется, страница с `page_type: page` создаётся как wysiwyg.
- Формы ответов десяти недокументированных операций, загрузки части файла, клонирования страницы и таблицы, статусов фоновых операций и комментариев совпадают со схемами официальной спецификации.

Не исправлено (на генерацию инструментов не влияет или неясно, кто прав):

- `UpdateCellSchema.value` (`update_grid_cells`): в официальной схеме поле обязательно (допускает `null`), в справочнике — нет. Оставлено обязательным: чтобы очистить ячейку, передавайте `value: null`.
- Ответы: в справочнике нет `PageAttributesSchema.is_available_for_ai`, `CellSchema.value` не обязательно, в перечислениях нет `move` (`B2BOperationType`), `cloud_page` (`PageType`), `avatars` (`StorageType`). Справочник упоминает поле ответа `last_revision_id` (через `fields=last_revision_id`), но настоящий API такого блока не знает (см. выше); в официальной схеме ответа его тоже нет.
- Размер части при загрузке: официальная спецификация говорит «все куски, кроме последнего, не меньше 5 МБ», справочник — «размер части ограничен настройками сервиса». Верхняя граница 16 МиБ взята из опыта старого сервера и указана только в описании `upload_file_part`.

## Пересборка

```bash
python3 -I crates/wiki-api/spec/build_openapi.py
python3 -I crates/wiki-api/spec/build_openapi.py --check
```

`--check` ничего не пишет и падает, если `wiki.openapi.json` не совпадает с пересборкой.

## Не отстал ли снимок от API

```bash
python3 -I crates/wiki-api/spec/spec_drift.py
```

Скрипт скачивает официальную спецификацию `https://api.wiki.yandex.net/v1/openapi.json` и оглавление документации `https://yandex.ru/support/wiki/ru/llms.txt` (обе публичные, токен не нужен) и печатает, чем они отличаются от файлов рядом:

- новые операции официальной спецификации; те, у которых нет записи в `overlay.json`, — отдельным разделом: без записи сборка из нового снимка упадёт, нужно выбрать имя, набор и уровень доступа;
- удалённые операции (с именем инструмента из дополнения);
- изменённые операции: какие поля изменились (параметры — с разбивкой по каждому, тело, ответы, описания), а также схемы `components`, на которые операция ссылается и которые изменились;
- новые, удалённые и изменённые компоненты и разделы вне операций (`info`, `servers` и другие);
- страницы операций справочника из `llms.txt` (`api-ref/<раздел>/<страница>`, без обзоров разделов), на которые не ссылается ни одна операция дополнения (`externalDocs.url`), и страницы из дополнения, которых в `llms.txt` больше нет.

Если расхождений нет, stdout пуст, а в stderr — одна строка с числом операций и страниц. Код выхода: `0` — изменений нет, `3` — есть расхождения, `1` — источник недоступен или отдал не то (например, вместо JSON — страница ошибки), `2` — неверные аргументы. `--spec <файл>` и `--llms <файл>` берут уже скачанные файлы вместо сети, `--skip-llms` не сравнивает страницы справочника. Файлы репозитория скрипт не меняет.

В CI проекта та же команда запускается отдельной проверкой раз в неделю и вручную; при расхождении задача завершается с ошибкой, отчёт — в логе. Обычные проверки запускают скрипт без сети (`--spec wiki.upstream.json --skip-llms`), чтобы видеть его поломку.

## Обновление снимка

```bash
curl -fsSL https://api.wiki.yandex.net/v1/openapi.json \
  | python3 -c 'import json,sys; json.dump(json.load(sys.stdin), sys.stdout, ensure_ascii=False, indent=2); print()' \
  > crates/wiki-api/spec/wiki.upstream.json
python3 -I crates/wiki-api/spec/build_openapi.py
```

Если в снимке появилась операция без записи в дополнении или пропала операция из дополнения, скрипт падает и называет её. После обновления сверьте расхождения выше: часть исправлений может стать лишней. Что именно изменилось, заранее показывает `spec_drift.py`; после обновления он должен давать пустой отчёт (новой странице справочника нужна ссылка из `externalDocs.url` операции).
